# Compose Desktop preview variants research

Research snapshot: 2026-10-27; checkout `14e9a6933617c8352b48e3df583dcf55a0cb85a3`, Compose Multiplatform 1.12.1, Roborazzi 1.76.0 and ComposablePreviewScanner 0.9.0. This is a source review, not a verified implementation or an IDE/scanner run. Here “orientation” means landscape versus portrait viewport, not LTR versus RTL.

## Recommendation

Represent the full 2 × 2 × 2 matrix explicitly: light/dark × English/Arabic × landscape/portrait. Give each case a unique name and concrete `widthDp`/`heightDp`, and pass the same dimensions, theme and locale to the Azkar preview surface. Use eight separate preview functions with explicit wrappers as the most conservative fallback if one multipreview cannot select a different wrapper for each variant. A custom annotation containing eight complete `@Preview` entries is worth a small proof of concept, but composing separate light/dark, locale and size multipreview annotations does **not** form a Cartesian product: Android's documentation says they are independent. [Android preview documentation](https://developer.android.com/develop/ui/compose/tooling/previews#multiple-previews)

An annotation's `uiMode`, `locale` and dimensions do not automatically change Azkar's explicit wrapper arguments: `AzkarPreviewSurface` defaults to light, English and default window dimensions; `AzkarTheme` derives layout direction and typography from its `uiLocale`; `AzkarThemePreview` derives `LocalWindowSizeClass` from its own dimensions. Thus a dark annotation wrapped in the default provider can still use the light app theme, and a portrait annotation alone does not necessarily select the matching responsive branch. See [preview annotations](../app/src/main/kotlin/com/azkar/ui/theme/AzkarPreviewAnnotations.kt), [preview surface](../app/src/main/kotlin/com/azkar/ui/theme/AzkarThemePreview.kt), and [theme](../app/src/main/kotlin/com/azkar/ui/theme/Theme.kt). Preview fixtures also need their own locale passed explicitly where they construct locale-dependent state.

## Locale is a separate constraint

In [Compose 1.12.1 resource source](https://github.com/JetBrains/compose-multiplatform/blob/v1.12.1/components/resources/library/src/commonMain/kotlin/org/jetbrains/compose/resources/ResourceEnvironment.kt), composable resource selection uses `Locale.current`, theme and density, cached with `remember`; the `ComposeEnvironment` override and constructor are internal. The [1.12.1 desktop implementation](https://github.com/JetBrains/compose-multiplatform/blob/v1.12.1/components/resources/library/src/desktopMain/kotlin/org/jetbrains/compose/resources/ResourceEnvironment.desktop.kt) reads the JVM default for non-composable resource access. Setting `LocalUiLocale` or `LocalLayoutDirection` therefore does not by itself establish Arabic resource strings. The local [locale activation](../app/src/main/kotlin/com/azkar/i18n/LocaleStore.kt) uses `Locale.setDefault`; the app rebuilds keyed content when switching locale. JetBrains' [desktop localization example](https://kotlinlang.org/docs/multiplatform/compose-resource-environment.html) likewise changes the JVM default and keys content, but is live documentation rather than version-pinned proof of preview behavior.

Roborazzi 1.76.0 documents applying preview `locale` by setting and restoring the JVM default around a capture, `uiMode` via the desktop system-theme local, and dimensions via a fixed-size box at density 1; `device` is unsupported. [Roborazzi 1.76.0 README](https://github.com/takahirom/roborazzi/blob/1.76.0/README.md#experimental-compose-desktop-preview-support). This is process-global locale state: serialize differently localized captures and restore the original on failure. Locale caching and preview reuse mean actual translated strings must be checked, especially when English and Arabic run in one JVM. Avoid mutating the JVM default from composable preview bodies: concurrent IDE renders and disposal make restore ordering unsafe. Separate IDE processes configured for one locale each are a possible isolation fallback, but do not demonstrate eight simultaneous correct IDE previews.

## IDE and scanner limits

JetBrains documents the multiplatform AndroidX preview annotation from 1.10 onward, but its current [IDE preview setup](https://kotlinlang.org/docs/multiplatform/compose-previews.html) says common-code IDE previews require an Android target. It does not establish this JVM-only project's exact IDE behavior, per-variant resource locale, or wrapper discovery. A [JetBrains tooling issue](https://youtrack.jetbrains.com/projects/CMP/issues/CMP-9500/MultiPreviews-not-detected-by-IDE-preview-feature) reports version-specific multipreview discovery failures and a local annotation workaround; verify the installed IDE and plugin rather than generalizing from the issue. Explicit functions with their own wrappers are a fallback for discovery, but still require proof that the IDE supplies the intended resource locale. Do not claim annotation labels establish Arabic strings.

The checked-out [Gradle configuration](../app/build.gradle.kts) enables the desktop scanner by default, scans `com.azkar.ui`, includes private previews, and uses a custom tester and checked-in `src/test/roborazzi/previews` references. The [custom tester](../app/src/test/kotlin/com/azkar/ui/preview/AzkarDesktopPreviewTester.kt) captures the tagged app surface; wrapper and scan option interaction needs an actual run. Roborazzi labels Desktop scanning experimental, and its desktop goldens differ from Android's. Existing named preview images show prior captures, not proof that all eight combinations, annotations, locale switching or IDE rendering work correctly in this checkout.

Before adopting a design, use a small deterministic probe containing a known English/Arabic resource, visible theme colors, direction-sensitive layout, and a responsive breakpoint. Verify eight distinct names and images in both the actual IDE and scanner, resource text and RTL/LTR, canvas dimensions and app window-size class, plus locale restoration across consecutive captures. Run record then verify on the supported CI host and inspect the resulting reference changes; retain explicit interaction tests, which static preview captures do not replace. If IDE localized resources cannot be isolated, document that limitation and use separately executed scanner cases or explicit screenshot tests for reliable locale coverage instead of presenting the IDE matrix as validated.
