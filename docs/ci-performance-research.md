# GitHub Actions performance review

## Priorities

1. Run the TypeScript and Chromium checks alongside the Linux Gradle build. This is the clearest way to reduce PR wait time while keeping the existing checks.
2. Warm the Intel macOS packaging cache from trusted `dev` release runs. Intel packaging determined when publishing could start in every packaging run sampled.
3. Measure restore-only Gradle caching in reviewed PRs. The existing trusted Linux cache gives this experiment a starting point.

For Linux Gradle, measure setup plus build time with and without restore. CI currently disables Gradle User Home caching, while trusted default-branch release validation writes Linux entries. The cache inventory showed a recent dependency entry of about 453 MB, so measure restored bytes, download avoidance and task outcomes before drawing a conclusion. **Warm Intel macOS first.** Intel logs showed cold Gradle User Home restores across the sampled releases. In beta.30 both macOS architectures missed and downloaded the Gradle distribution, while Linux packaging restored the Linux validation cache. The packaging matrix can read caches but only Linux validation writes, so there is currently no matching writer for macOS. Start with an Intel packaging writer restricted to trusted scheduled/manual releases on default-branch `dev`. Keep tags and PRs restore-only. Verify a real warm hit on a later Intel job and measure through artifact upload, including writer overhead. If it still leads, profile compilation, ProGuard, and DMG creation separately before considering a larger runner or artifact reuse. Keep native installer and smoke coverage. ## November 27 follow-up on PR CI

The latest 100 CI runs included 36 successes, 34 cancellations, 24 failures and six skips. These are latest outcomes for *runs*. For example, the first attempt on f700b01 failed in the Linux build and the latest attempt succeeded. They are unsuitable as a first-attempt failure rate. I inspected job breakdowns for the most recent 22 runs and used the seven newest successful runs for the timings below. [CI history](https://github.com/jamhour1g/Azkar-App/actions/workflows/ci.yml) · [First attempt](https://github.com/jamhour1g/Azkar-App/actions/runs/45949737445/attempts/1) · [Successful retry](https://github.com/jamhour1g/Azkar-App/actions/runs/45949737445)

**Pilot a smaller check for download-site-only PRs targeting dev.** Linux took a median 5m 53s (range 5m 31s to 6m 17s). The parallel site and scripts job took a median 2m 22s. Start with a narrow allowlist such as site/src/** and site/tests/**. Keep the site build, Chromium tests, reviewed merge revision checks and required status. Shared manifests and lockfiles, hosted installers, workflow changes, mixed changes, unknown paths and promotion PRs should keep full coverage. Test renames in both directions. The Linux job alone cost about six runner-minutes in these samples. The wall-clock difference between median job durations is 3m 31s, an estimate for eligible PRs. [Linux and site jobs](https://github.com/jamhour1g/Azkar-App/actions/runs/45948518197) · [Earlier sample](https://github.com/jamhour1g/Azkar-App/actions/runs/45555475160) · [CI selection](https://github.com/jamhour1g/Azkar-App/blob/8e5b6a07228f66d9ed3d082bd3042d91ecea712a/.github/workflows/ci.yml#L105-L145)

**Profile app configuration before changing more caches.** The hosted Gradle profile measured 5m 19s overall, including 49.5s configuring projects, 44.4s of it in :app. The largest app tasks were Kotlin compilation (64.8s), ProGuard (47.2s) and tests (45.3s). Gradle runs tasks in parallel, so these durations cannot be added to predict elapsed savings. Measure expensive configuration in the app and its applied plugins, then compare equivalent hosted runs with the same tasks. The project records a daemon handshake failure with configuration caching. An automatic run for the same SHA had started nine seconds before dispatch and was cancelled at 06:26:45. ## Release follow-up, 2026-11-27

Five consecutive Release runs on `dffc2e9` failed on November 25–27. Four reached Pages deployment and failed during live verification. The fifth stopped in Linux packaging when Maven returned HTTP 429 for `:app:checkRuntime`. Open PR #38 covers that retry, the maintenance-only release gate, cache changes and the Pages marker exception. PR #39 builds on #38 and checks draft assets before publication. These runs predate both PR heads. 1. **Check the Pages archive against the expected public files before deployment.** The November 27 checksum artifact lists 71 paths, starting with `./.nojekyll`. The pinned Pages action excludes hidden files by default. Live verification reads paths in order and received six 404 responses on its first download. By then all four installer jobs had succeeded. #38 excludes this one marker, but a future difference between the archive filter and checksum generator can still reach production. Add a test fixture containing the marker, a public file and a nested hidden file. At release time, compare the actual Pages tar member list with the intended public file list before allowing deploy. Report missing and unexpected paths. Keep the live checksum check for what Pages actually serves.
