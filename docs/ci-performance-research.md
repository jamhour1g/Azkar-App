# GitHub Actions performance review

## Priorities

1. Run the TypeScript and Chromium checks alongside the Linux Gradle build. This is the clearest way to reduce PR wait time while keeping the existing checks.
2. Warm the Intel macOS packaging cache from trusted `dev` release runs. Intel packaging determined when publishing could start in every packaging run sampled.
3. Measure restore-only Gradle caching in reviewed PRs. The existing trusted Linux cache gives this experiment a starting point.

Move the JavaScript setup, TypeScript checks and browser tests to a sibling job that starts after approval. The browser tests currently run before the gallery capture and already work without the generated gallery. Retain both merge-parent checks, the existing documentation-only skip, and the required status on the reviewed SHA. Have the status reporter require both Linux and site success. The observed slow run could have saved roughly six minutes with comparable runner starts and setup. The fast Chromium run offered roughly 45–55 seconds. These are estimates from the serial timings. A second runner adds some setup and total runner time. For Linux Gradle, measure setup plus build time with and without restore. CI currently disables Gradle User Home caching, while trusted default-branch release validation writes Linux entries. The cache inventory showed a recent dependency entry of about 453 MB, so measure restored bytes, download avoidance and task outcomes before drawing a conclusion. Enforce read access with GitHub's scoped `cache-mode: read` for jobs executing reviewed PR code, including the manual dispatch path, and set Gradle's `cache-read-only: true`. Check lint support for the GitHub key before rollout. Gradle task output caching and parallel execution are already enabled. Gallery capture costs only 11–14 seconds after the build and reuses its outputs. The independent Kotlin release-script suite costs about one minute and is a lower-priority parallelization candidate. **Warm Intel macOS first.** Intel logs showed cold Gradle User Home restores across the sampled releases. In beta.30 both macOS architectures missed and downloaded the Gradle distribution, while Linux packaging restored the Linux validation cache. The packaging matrix can read caches but only Linux validation writes, so there is currently no matching writer for macOS. Start with an Intel packaging writer restricted to trusted scheduled/manual releases on default-branch `dev`. Keep tags and PRs restore-only. Verify a real warm hit on a later Intel job and measure through artifact upload, including writer overhead. If it still leads, profile compilation, ProGuard, and DMG creation separately before considering a larger runner or artifact reuse. Keep native installer and smoke coverage. **Keep the same-run Kotlin dependency handoff and measure it on GitHub.** Both beta.30 publishing attempts hit Maven Central HTTP 429 at draft preparation. A different release run hit HTTP 429 earlier in Gradle validation. The existing local workflow change reuses Kotlin scripting dependencies from validation for publishing, which addresses the duplicate cold fetch at draft preparation. Gradle caching and the first Kotlin script resolution are separate paths. Track artifact transfer time and whether the first download still needs its own reliability fix. [First draft failure](https://github.com/jamhour1g/Azkar-App/actions/runs/45359921829/job/138333106285#logs) · [Second draft failure](https://github.com/jamhour1g/Azkar-App/actions/runs/45359921829/job/138336938909#logs) · [Gradle validation failure](https://github.com/jamhour1g/Azkar-App/actions/runs/45336649659/job/138250541575#logs)

**Move release-site work off the publishing path only after packaging improves.** The publish job took 1m 35s to 1m 59s on the three successful historical samples. Preparing the website after screenshots could overlap Intel packaging, but a split adds a runner and artifact transfer. Keep signing, Pages deployment, live checksum verification, and public release publication in their existing gated order. The scheduled no-release check took about 55 seconds in the November 23 sample and is a lower priority for release latency. ## Verification

Rehearse the CI job split with an approved owner PR and check success, browser failure and documentation-only skip reporting. Rehearse an installer run to verify both required statuses. Compare several matched runs and track queue delay, wall-clock time and total runner time separately. For release caching, compare cold and warm Intel runs with the same task and runner label before expanding writes. The review uses representative hosted runs and repository source. No proposed speed changes were benchmarked on a hosted runner.
